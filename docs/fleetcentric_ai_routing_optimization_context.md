# fleetcentric.ai: Routing and Route Optimization Context

You are helping with a university shuttle-bus transport management system called **fleetcentric.ai**.

The project manages:

- Students and student profiles
- Semesters and registration periods
- Routes
- Pickup and drop-off stops
- Ordered route stops
- Buses and drivers
- Route assignments per semester
- Student transport registrations
- Seat allocation
- Bus GPS tracking
- Off-route detection
- Complaints, incidents, and notifications
- Admin route creation and editing
- Student and admin route maps

The backend is built with **Django and Django REST Framework**. The frontend is built with **React and Vite**. Maps are rendered using **MapLibre GL**.

## Core route data model

### Route

A route contains:

- `name`
- `description`
- `is_active`
- `status`: `draft`, `published`, or `archived`
- `geometry`: stored as GeoJSON, normally a `LineString`
- `geometry_updated_at`

The stored geometry is intended to be a road-following route generated by a routing provider.

### Stop

A stop contains:

- `name`
- `latitude`
- `longitude`
- `address`
- `is_active`
- Optional location metadata such as provider place ID and accuracy

### RouteStop

`RouteStop` connects a route to a stop and stores:

- Route
- Stop
- `stop_order`
- Morning ETA
- Evening ETA

The `stop_order` field determines the sequence in which the bus visits stops.

Database constraints ensure that:

- A stop cannot appear more than once on the same route.
- A route cannot have duplicate stop-order values.
- Stop order must be positive.

The ordered `RouteStop` records are the source of truth for the route sequence.

## Current routing provider

The backend currently uses an OSRM compatible routing provider.

The default routing URL is:

```text
https://router.project-osrm.org
```

It can be overridden with:

```text
MAP_ROUTING_URL
```

The backend sends requests in this form:

```text
{MAP_ROUTING_URL}/route/v1/driving/{longitude,latitude;longitude,latitude;...}
```

The request parameters are:

```json
{
  "overview": "full",
  "geometries": "geojson"
}
```

The provider returns a GeoJSON `LineString` containing many coordinates that follow the road network.

GeoJSON coordinates use this order:

```text
[longitude, latitude]
```

Example:

```json
{
  "type": "LineString",
  "coordinates": [
    [67.084889, 24.921628],
    [67.084966, 24.921534],
    [67.085050, 24.921433],
    [67.085701, 24.920646]
  ]
}
```

## Current route creation and editing flow

The admin route builder allows an administrator to:

1. Select a route.
2. Add available stops.
3. Remove stops.
4. Reorder stops.
5. Edit morning and evening ETAs.
6. Create new stops.
7. Edit stop coordinates and addresses.
8. Preview the route.
9. Save and publish the route.

The stop order is currently selected manually by the administrator.

When selected stops change, the frontend calls:

```text
POST /api/admin/maps/route-preview/
```

The request contains:

```json
{
  "stop_ids": [12, 4, 8, 19]
}
```

The backend:

1. Validates that there are between 2 and 60 stops.
2. Converts IDs to integers.
3. Rejects duplicate stop IDs.
4. Rejects inactive or missing stops.
5. Rejects invalid coordinates.
6. Preserves the submitted order.
7. Sends the ordered coordinates to OSRM.
8. Returns road geometry.

Example response:

```json
{
  "geometry": {
    "type": "LineString",
    "coordinates": [
      [67.08, 24.92],
      [67.081, 24.921],
      [67.083, 24.923]
    ]
  },
  "source": "provider"
}
```

Possible `source` values are:

- `provider`
- `cache`
- `fallback`

When a route is saved, the frontend submits the selected stops, their ETAs, the generated geometry, and the route status. The backend replaces the route's ordered `RouteStop` records inside a database transaction and stores the submitted geometry on the `Route`.

## Current routing behavior

The current routing implementation is **not an optimization algorithm**.

It is a waypoint-routing system:

```text
Given an already ordered list of stops,
find a road-following path through those stops in that order.
```

For example:

```text
Stop A -> Stop B -> Stop C -> Stop D
```

The system asks OSRM to calculate a driving route through:

```text
A -> B -> C -> D
```

It does not currently decide whether that order is optimal. The route order is manually selected by an administrator.

## Geometry caching

The backend caches successful provider geometry using a cache key derived from the ordered stop coordinates.

The cache key is conceptually based on:

```text
longitude1,latitude1;longitude2,latitude2;...
```

Successful provider geometries are cached for approximately seven days.

Only successful provider results are cached. Fallback straight-line geometry is not cached.

This prevents a temporary OSRM failure from permanently saving a straight line as the route geometry.

## Fallback behavior

If routing fails, the backend returns a fallback `LineString` containing only the stop coordinates:

```json
{
  "type": "LineString",
  "coordinates": [
    [longitude_of_A, latitude_of_A],
    [longitude_of_B, latitude_of_B],
    [longitude_of_C, latitude_of_C]
  ]
}
```

This fallback connects stops directly and does not follow roads.

The frontend route-preview helper also has a fallback. If the backend preview request fails, it returns the ordered stop coordinates directly.

Therefore, a routing-provider failure can still result in a visually valid map line, but the line may be straight rather than road-following. For future work, the interface should make this state explicit, for example:

```text
Road routing unavailable. Preview is showing straight-line connections.
```

## Stale geometry detection

The backend detects old straight-line geometries that may have been saved during a previous provider outage.

It checks whether stored geometry:

- Is a valid GeoJSON `LineString`.
- Starts at the first route stop.
- Ends at the last route stop.
- Has all intermediate points approximately collinear.

If so, it treats the geometry as a stale straight-line fallback and retries the routing provider.

This is more robust than exact coordinate-array comparison because a fallback line may be rounded or contain interpolated points.

```text
GET /api/routes/{id}/map-detail/
```

It returns the same compact map-oriented structure for one route.

The endpoint recalculates or refreshes geometry when:

- Stored geometry is missing.
- Stored geometry is invalid.
- Stored geometry is recognized as a straight-line fallback.

## Important optimization problem distinction

Several different optimization problems may apply. They should not be treated as the same problem.

### 1. Stop ordering

Given a fixed set of stops, determine the best visiting order.

Possible algorithms include:

- Traveling Salesman Problem
- TSP with a fixed depot
- Open TSP
- 2-opt
- 3-opt
- Lin-Kernighan
- Simulated annealing
- Genetic algorithms
- Ant colony optimization

Example:

```text
Given stops A, B, C, D,
find the shortest route beginning at the depot
and visiting all stops once.
```

### 2. Student-to-stop assignment

Students may live at different locations and need to be assigned to pickup stops.

Possible objectives include:

- Minimize walking distance.
- Keep each student within a maximum walking distance.
- Balance students across stops.
- Prevent a stop from becoming overcrowded.
- Prefer stops near main roads.
- Respect accessibility and safety requirements.

This is separate from stop ordering.

### 3. Vehicle routing

If multiple buses are available, the problem becomes a Vehicle Routing Problem.

Possible variants include:

- Capacitated Vehicle Routing Problem
- Vehicle Routing Problem with Time Windows
- Multi-depot Vehicle Routing Problem
- Heterogeneous Fleet Vehicle Routing Problem
- School Bus Routing Problem
- Pickup and Delivery Problem
- Dial-a-Ride Problem

Potential constraints include:

- Bus capacity
- Maximum route duration
- Maximum route distance
- Driver availability
- Bus availability
- Semester assignment
- Start and end depots
- Campus arrival deadline
- Maximum ride time per student

### 4. Route scheduling

After routes are created, buses and drivers must be scheduled. This may include:

- Morning departures
- Evening return trips
- Driver working hours
- Bus availability
- Semester assignments
- Maintenance periods
- Multiple routes sharing buses
- Required arrival deadlines

### 5. Dynamic routing

The current system uses mostly static route geometry. A future dynamic system could account for:

- Traffic
- Road closures
- Bus GPS location
- Delays
- Off-route events
- Weather
- Temporary blocked roads
- Changed stop availability

This is different from pre-semester route planning.

## Possible optimization objectives

The project should define its objectives before selecting an algorithm.

Possible objectives include:

```text
Minimize total route distance
```

```text
Minimize total route duration
```

```text
Minimize total fuel cost
```

```text
Minimize the maximum student ride time
```

```text
Minimize average student walking distance
```

```text
Minimize the number of buses
```

```text
Maximize the number of students served
```

```text
Balance route sizes and bus loads
```

A combined objective could be represented as:

$$
\text{Cost} =
w_1(\text{distance})
+
w_2(\text{travel time})
+
w_3(\text{walking distance})
+
w_4(\text{ride-time penalty})
+
w_5(\text{capacity violation penalty})
$$

The weights should reflect institutional priorities.

For example, minimizing total distance may produce routes that are efficient overall but inconvenient for individual students. A slightly longer route may be preferable if it significantly reduces walking distance or maximum ride time.

## Recommended research direction

Research should begin with the **School Bus Routing Problem** because the project has:

- Students
- Pickup stops
- Buses
- Bus capacity
- Arrival deadlines
- Morning and evening trips
- Student ride-time concerns

Other relevant topics are:

### Capacitated Vehicle Routing Problem

Relevant when:

- A route has more students than one bus can carry.
- Multiple buses are available.
- Students need to be divided between buses or routes.

### Vehicle Routing Problem with Time Windows

Relevant if:

- Students have pickup-time constraints.
- The bus must reach campus before a specific time.
- Routes have morning and evening ETA requirements.
- There are maximum waiting times.

### Multi-objective optimization

Relevant if the system must balance:

- Distance
- Duration
- Capacity
- Walking distance
- Fairness
- Number of buses
- Student ride time

### Road-network optimization

The current OSRM geometry is a road-network path. If deeper optimization is needed, relevant subjects include:

- Road graphs
- Dijkstra's algorithm
- A*
- Contraction hierarchies
- Time-dependent shortest paths
- Travel-time matrices

It is usually better to let OSRM, GraphHopper, or OpenRouteService handle road-level shortest-path calculations and use an optimization algorithm above them to decide stop assignments and ordering.

## Suggested future architecture

A possible future architecture is:

```text
Student locations
        |
        v
Stop assignment algorithm
        |
        v
Candidate stops per route
        |
        v
Route ordering / vehicle routing optimizer
        |
        v
Ordered stop sequences
        |
        v
OSRM or another routing engine
        |
        v
Road geometry and route duration
        |
        v
Human review in the admin route builder
        |
        v
Saved RouteStop records and Route.geometry
```

The optimizer could produce data like:

```json
{
  "routes": [
    {
      "bus_id": 4,
      "stop_ids": [12, 4, 8, 19],
      "estimated_distance_m": 18400,
      "estimated_duration_s": 3200,
      "students_served": 28,
      "capacity_used": 28
    }
  ]
}
```

The administrator should be able to review and modify the result before publishing it.

A fully automatic optimizer should not immediately overwrite manually configured routes. A safer workflow is:

1. Generate an optimized proposal.
2. Display proposed routes on the map.
3. Show metrics and constraint violations.
4. Allow administrator edits.
5. Publish only after approval.

## Important technical recommendation

Do not use raw latitude/longitude Euclidean distance as the final route cost.

The map uses geographic coordinates, but real road distance and travel duration must come from a routing engine.

A useful optimization architecture would be:

1. Build a travel-time or travel-distance matrix between all candidate stops.
2. Use that matrix in the optimization algorithm.
3. After optimization, call OSRM again to obtain the final detailed road geometry.

Conceptually:

```text
Stop coordinates
        |
        v
OSRM table/matrix API
        |
        v
Distance/time matrix
        |
        v
TSP/VRP/constraint optimization
        |
        v
Ordered stop sequences
        |
        v
OSRM route API for final geometry
```

The OSRM `table` service may be useful because it can provide pairwise travel times and distances between stops without requesting full geometry for every possible sequence.

## Short handoff summary

fleetcentric.ai is a Django REST Framework backend with a React/Vite frontend for university shuttle transportation. Routes consist of ordered `RouteStop` records. Each stop has latitude, longitude, address, and optional morning/evening ETA. Administrators currently manually choose and order stops in the route builder.

The backend sends the ordered stop coordinates to an OSRM-compatible routing service using the OSRM `/route/v1/driving/{coordinates}` endpoint with `overview=full` and `geometries=geojson`. OSRM returns a road-following GeoJSON `LineString`, which is stored in the `Route.geometry` JSON field and displayed by the React MapLibre map component. Successful route geometries are cached for seven days. If routing fails, the system returns a straight-line fallback through the stop coordinates, which is not cached. The backend also detects old collinear fallback geometries and retries routing.

The current system performs waypoint routing only. It does not optimize stop order, assign students to stops, assign stops to buses, minimize route distance, balance bus capacity, or optimize multiple routes. The route order is manually entered through `RouteStop.stop_order`.

The most relevant research topics are:

- School Bus Routing Problem
- Capacitated Vehicle Routing Problem
- Vehicle Routing Problem with Time Windows
- Multi-depot Vehicle Routing Problem
- Heterogeneous Fleet Vehicle Routing Problem
- Student-to-stop assignment optimization
- Multi-objective optimization
- OR-Tools and constraint programming
- 2-opt, 3-opt, simulated annealing, genetic algorithms, and ant colony optimization
- OSRM table/matrix APIs for travel-time and distance matrices

A likely first implementation would use Google OR-Tools or another VRP solver, with OSRM supplying realistic road travel-time and distance matrices. The optimizer should generate proposals for administrator review instead of immediately replacing manually configured routes.
